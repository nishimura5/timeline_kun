# macOSでの外部アプリへのショートカット送信（dev110仕様検討）

## 結論と今回の対応

macOSにも指定アプリへキーイベントを送るAPIはある。ただし、アプリの
指定と、その中の特定ウインドウの指定は別の問題である。既存の
`window_title`だけの設定をMacでも有効にすることは見送る。

dev110では既存のWindows専用仕様を維持し、macOS/Linuxの`window_key`は
明示的な未対応として扱う。今回、`WindowKeyAction`の直接呼び出しにも
実行前のOS判定を追加した。Mac用送信バックエンドは実装・実機検証していない。

| 経路 | macOS/Linuxでの動作 |
| --- | --- |
| 設定読込 | 既存形式を検証して保持する。Windowsの設定を持ち込んでも送信しない。 |
| `Check Windows` | 未対応の案内のみ。ウインドウ探索・前面化・キー送信をしない。 |
| `ActionManager` | 設定済み`window_key`は未対応アクションに解決する。登録済み実体でも迂回しない。 |
| `WindowKeyAction.connect/start/stop`の直接呼び出し | 探索・キー変換・バックエンド生成より前に`False`を返す。 |
| タイマー | 動作を継続する。送信要求は失敗として既存のアクションログに記録する。GoPro/BLEは別扱い。 |

状態表示は`WindowKey actions are supported on Windows only.`とする。
WindowsのCTRL/WINをMacのCOMMAND等に自動変換せず、アクティブな別アプリへの
汎用キー送信にも代替しない。

## Apple APIで可能なことと制約

- [AXUIElementPostKeyboardEvent](https://developer.apple.com/documentation/applicationservices/1462057-axuielementpostkeyboardevent)
  は送信先アプリを指定できる。Appleの説明では受け取るAX要素はアプリまたは
  システム全体の要素に限られる。ウインドウのAX要素を直接渡すことはできない。
  システム全体の要素を渡すとアクティブアプリ宛てになるため、今回の用途では使わない。
- [CGEvent.postToPid](https://developer.apple.com/documentation/coregraphics/cgevent/posttopid(_:))
  もPIDを指定する候補だが、特定ウインドウの宛先指定ではない。
- Accessibilityクライアントの信頼状態は
  [AXIsProcessTrustedWithOptions](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions)
  で確認できる。権限があることと、対象アプリが必要なAX操作に対応していることは
  別に検証する。AXキー送信は未実装・通信失敗等のエラーを返し得る。

以上から「Macでは指定アプリへの送信が一切不可能」とは判断しない。
一方、これらのAPIだけで任意のアプリ内の任意のウインドウへの確実な配送を
保証できるとも判断しない。キー送信の成功と対象アプリの録画開始等の成功も別である。

## 将来のMac対応案（未実装）

Windows設定の暗黙的な流用を避け、Mac向けの明示的なアクション形式を設ける。
アプリ識別にはbundle identifierを使い、実行時に起動中プロセスを一意に特定する。
PIDは設定に固定保存せず、送信ごとに解決・再確認する。ウインドウ指定が必要な場合は
そのアプリ内でタイトルを完全一致させ、候補が0件または複数なら失敗にする。

対応を有効にするための条件は次のとおり。

1. 権限確認と対象探索は送信しない事前確認として提供する。権限要求はユーザーの
   明示操作で行い、タイマー実行中にダイアログを開いたり許可待ちしたりしない。
2. アプリ宛てだけの送信と、特定ウインドウを要求する送信の意味を区別する。
   後者は必要なAX操作で対象を選択し、直前に対象PIDと選択ウインドウを再確認できる
   アプリに限る。選択と送信の間の競合も検証し、安全性を確認できなければ非対応とする。
3. 未起動、複数候補、権限不足・取消、AX未対応、対象終了、選択失敗時には
   キーを送らず理由を返す。アプリ自動起動やグローバル送信への代替を行わない。
4. COMMAND/CMD、OPTION/ALT、CONTROL/CTRL、SHIFT等の対応キーと配列を定義し、
   送信前に検証する。Windowsの仮想キーコードは流用しない。途中失敗時のキー解放も
   同じ送信先に限定する。成否不明の送信を自動再試行しない。
5. 送信結果のログは「イベント送信」と「対象処理の完了」を区別する。
   対象アプリが状態取得APIを提供しなければ、処理完了は未確認とする。

実機で確認する項目は、別アプリの前面表示、同一アプリの複数ウインドウ・同名
ウインドウ、最小化、別Space、モーダルダイアログ、送信直前の対象終了・再起動、
権限取消、修飾キーとキー配列の違い。Pythonからの起動と配布版の両方で確認する。
特定ウインドウへの安全性が確認できない場合は、アプリ宛て操作として成立する用途に
対応範囲を限定するか、引き続き未対応とする。対象アプリが専用APIを提供する場合は、
キー送信と比較してそのAPIによる制御も検討する。
